# Spike 0.2-B1: OpenUSD v26.08 on Ubuntu 26.04

Date: 2026-10-14. Question: can we build OpenUSD from source for the `openusd_vendor` package
(docs/design/dependencies.md §4, risk R1), and does the schema plan of RFC 0002 work with it?

**Recommendation: go.** Pin v26.08, monolithic library, Python bindings on. Store schema units in
a registered metadata field (`lagrangeUnit`), not in customData.

## Setup

| Item | Value |
|---|---|
| Source | `PixarAnimationStudios/OpenUSD` tag `v26.08` (commit `ee47c67`, released 2026-07-20) |
| Machine | Ubuntu 26.04 amd64 with ROS 2 Lyrical installed, 20 threads, 30 GB RAM; build with `-j 16` |
| Toolchain | GCC 15.2.0, CMake 4.2.3, Ninja, system TBB 2022.3.0 (`libtbb-dev`), Python 3.14.4 |
| Not tested | arm64; a clean `ros:lyrical` container (this host has the same packages, but a container run is still owed before the CI cache is built) |

CMake options (all verified in v26.08's `cmake/defaults/Options.cmake`):

```
-DCMAKE_BUILD_TYPE=Release -DPXR_BUILD_MONOLITHIC=ON -DPXR_BUILD_USD_TOOLS=ON
-DPXR_BUILD_IMAGING=OFF -DPXR_BUILD_USD_IMAGING=OFF -DPXR_BUILD_USDVIEW=OFF -DPXR_BUILD_EXEC=OFF
-DPXR_ENABLE_GL_SUPPORT=OFF -DPXR_BUILD_TESTS=OFF -DPXR_BUILD_EXAMPLES=OFF
-DPXR_BUILD_TUTORIALS=OFF -DPXR_ENABLE_PYTHON_SUPPORT=OFF|ON
```

No `build_usd.py`, no downloaded dependencies, no patches.

## Results

| Configuration | Configure | Build + install | Install size | Warnings |
|---|---|---|---|---|
| C++ only | 1 s | 286 s | 56 MB (`libusd_ms.so` + plugins + 6 tools) | 4, none in our use |
| C++ + Python 3.14 | 1 s | 726 s | 159 MB, adds `usdGenSchema` and the `pxr` Python package | 4 |

The four warnings are the same in both builds: one `-Woverloaded-virtual` ("was hidden") in
`usdUtils/assetLocalizationDelegate.h`, and three `-Warray-bounds` reports inside libstdc++
headers (`std::array<double, 5>`) from an OpenUSD source file. None stop the build; the
array-bounds ones look like known GCC false positives but were not investigated.

## Checks

1. **Python 3.14 bindings** build and import (`from pxr import Usd, Sdf, Plug`). `usdGenSchema`
   runs with the system `python3-jinja2`.
2. **Codeless applied schema.** A one-attribute `ElectricalMotorAPI_1` with
   `skipCodeGeneration = true` generates `generatedSchema.usda` and `plugInfo.json`; loaded through
   `PXR_PLUGINPATH_NAME`, a prim with `apiSchemas = ["ElectricalMotorAPI_1"]` reports
   `HasAPI("ElectricalMotorAPI_1") == true` from Python and from C++.
3. **Version suffix (open question F3).** `Usd.SchemaRegistry.ParseSchemaFamilyAndVersionFromIdentifier("ElectricalMotorAPI_1")`
   returns `("ElectricalMotorAPI", 1)`. The `_N` suffix is the one USD understands.
4. **Units in customData do not work.** `usdGenSchema` clears every property's customData
   (`usdGenSchema.py` line 1906, `myproperty.ClearCustomData()`), and even when put back by hand,
   the schema registry refuses customData as a fallback field (`schemaRegistry.cpp` line 1795:
   "Disallow customData, since it contains information used by usdGenSchema"). A loader cannot
   read `customData["lagrange:unit"]` from schema definitions.
5. **A registered metadata field works.** A plugin `plugInfo.json` declaring
   `SdfMetadata: { "lagrangeUnit": { "type": "string", "appliesTo": ["attributes"] } }` lets the
   schema source write `double elec:windingResistance ( lagrangeUnit = "ohm" )`. The field
   survives `usdGenSchema`, appears in the prim definition (`ListMetadataFields()` includes
   `lagrangeUnit`), and resolves as a fallback on every authored attribute:
   `UsdAttribute::GetMetadata(TfToken("lagrangeUnit"), &unit)` gives `"ohm"` in C++ against the
   C++-only build.
6. **Consumer compile flags.** `pxr/base/tf/hashset.h` and `hashmap.h` include libstdc++'s
   deprecated `<ext/hash_set>`, which emits a `#warning` even through `-isystem`. Targets that
   include OpenUSD headers define `_GLIBCXX_PERMIT_BACKWARD_HASH` (verified to silence it) and
   use `SYSTEM` include directories, so `-Werror` builds stay clean.

## Consequences

- `openusd_vendor` builds v26.08 with the options above, Python on: `usdGenSchema` is needed to
  build `lagrange_schemas`, and the bindings work with the system Python. The C++-only variant
  stays possible if build time becomes a problem (5 min instead of 12).
- RFC 0002 convention 3, `docs/design/formats.md` §2 and open question F4 now say
  `lagrangeUnit` instead of `customData["lagrange:unit"]`. `lagrange_schemas` must ship the
  `SdfMetadata` registration in its `plugInfo.json`, and every tool that opens our stages must
  load that plugin (otherwise the field is an unknown-metadata error when the layer is read).
- `lagrange::parseUnit` (core/signals) parses every unit string the design uses.

## Still open

- arm64 build time and a run inside the `ros:lyrical` container (next step for the CI cache).
- Whether the ROS buildfarm can build this (time limit, memory); R1 remains for debs.
- Whether third-party tools (usdview, Omniverse) show the field without our plugin: they will
  report unknown metadata on load unless the plugin is on their plugin path.
