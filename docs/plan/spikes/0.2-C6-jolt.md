# Spike 0.2-C6: a second rigid-body backend on Jolt Physics

Date: 2026-10-25. Roadmap item 0.2-C6: "Minimal Jolt backend running the pendulum and AMR.
**AC:** abstraction gaps listed; full backend scheduled."

## What was built

- `vendor/jolt_vendor`: Jolt Physics **v5.6.0** (the latest release, 11 July 2026; MIT, checked
  on GitHub), from the release tarball pinned by SHA-256, built Release and
  `CROSS_PLATFORM_DETERMINISTIC`, single precision.
  - The profiler, debug renderer, asserts and floating-point exceptions are off. Jolt turns them
    on per build configuration through public definitions that change struct layouts, so a
    consumer built in another configuration would disagree with the library.
  - Jolt 5.6's GPU compute (hair simulation) is off: it needs a shader compiler at build time,
    and rigid bodies do not use it. The library builds in about 18 s.
- `modules/rigid_body/jolt_backend` (`lagrange_rigid_body_jolt`): `JoltBackend`, an `IModule`
  with MujocoBackend's signal names for what it covers. It builds from the same world tables as
  MuJoCo:
  - Bodies joined by fixed joints become one Jolt body, with masses and inertias combined by the
    parallel-axis theorem. Each merged link still reports its own pose.
  - Hinges and slides become Jolt constraints. Joint torque is applied equal and opposite to
    the two bodies.
  - Static scenery and the ground plane are static bodies.
  - One robot's bodies do not collide with each other (a group filter), as with MuJoCo.
  - Stepping is single-threaded; Jolt's state recorder saves and restores the state.

## Abstraction gaps

These have to be closed before Jolt can replace MuJoCo in a run:

1. **Outputs the other domains read.** Not produced:
   - `body/<b>/acceleration`, which **the IMU reads**: a run with sensors does not wire on Jolt;
   - `joint/<j>/acceleration`, `effective_inertia` and `constraint_torque`, which electrical
     motor models and the coupling-stability check need;
   - the `joint/<j>/load_torque` input.

   Jolt has no direct equivalent of MuJoCo's `qacc` or constraint forces. Acceleration needs
   finite differences of velocity over the step, and the constraint torque needs the hinge's
   total lambda divided by the step.
2. **Backend selection.** The server hard-codes `MujocoBackend`, and the profile check accepts
   only `backend: mujoco`. A registry that maps `domains.rigid_body.backend` to a module factory
   is missing (`core/module` registry, RFC 0001).
3. **Contact model.** Friction is per body in Jolt; it is the largest friction among a merged
   group's colliders, combined between bodies by Jolt's default (geometric mean). MuJoCo's is
   per geom. `World::Colliders` has no restitution, stiffness or damping, so the two engines'
   defaults decide. `env/friction_scale` is not read.
4. **Joints.** Spherical joints are refused. There is no joint damping or friction, and no
   soft limits; `World::Joints` has no fields for them yet, which affects both backends.
5. **Merged links.** A link fixed to its parent has no body of its own in Jolt, so a wrench on
   it applies at the group's centre of mass. That is right for the motion, but there is no
   per-link reaction force.
6. **Precision.** Jolt is single precision here. With the floating origin keeping positions
   within about a kilometre this is enough for the AMR. `DOUBLE_PRECISION` should be measured
   before v0.7 (huge worlds).
7. **Determinism across machines.** Identical on one machine, single-threaded. Jolt's
   multi-threaded stepping is documented as deterministic, but that is unverified here. The
   vendor build enables AVX2, so binaries for other CPUs need a portable instruction set.
8. **Validation.** MuJoCo has the closed-form validation suite of spike 0.2-C1. A
   backend-neutral agreement suite (same scenarios, both engines, tolerances) is what v0.3's
   "Second rigid-body backend" acceptance needs.

## Scheduled

The full backend is v0.3's "Second rigid-body backend: Jolt backend complete" with
"Backend-agreement tests" (roadmap §4). In order: gap 2 (the registry, which also helps PhysX
later), gap 1 (the outputs, so sensors and electrical wire), gap 8 (the agreement suite), then
gaps 3 to 5. Gaps 6 and 7 go with v0.7 and packaging.

## Outcome (v0.3, 2026-10-25)

Gaps 1, 2 and 8 are closed, and part of 3: `JoltBackend` produces every signal MuJoCo does,
`--physics jolt` and a profile's `backend: jolt` select it, contact friction combines as
MuJoCo's (the larger), and `server/test/test_backends.cpp` is the agreement suite (numbers in
rigid_body.md §7). Rotor inertia is applied as joint torques computed from the joints'
inertia matrix (composite rigid bodies, base held still), half-relaxed against ringing.
Jolt's per-body angular velocity clamp (a game default of 47 rad/s, applied before the
constraint solve) discarded joint torques on light links and is raised. Still open: gaps 4 to
7, per-collider friction on merged bodies, and the drive wheels' load on rigid contacts
(progress.md, Known issues).
