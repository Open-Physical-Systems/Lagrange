# Spike 0.2-F7: `rosidl::Buffer` (desk study)

Date: 2026-10-25. Roadmap item 0.2-F7: "Publish a point cloud through `rosidl::Buffer` with the
CPU backend, then the CUDA backend. **AC:** report on copy counts and constraints; plan for
v0.6."

**Scope:** the CPU half from the installed headers and our bridge's code. The CUDA half could
not be run: the development machine has an Intel GPU, and the CUDA backend needs NVIDIA's
driver and toolkit. Statements about CUDA come from the package metadata, not from a run.

## What Lyrical ships

| Package (`ros-lyrical-*`) | What it is |
|---|---|
| `rosidl-buffer` | `rosidl::Buffer<T>`: a vector-like container with a pluggable implementation; the default is `CpuBufferImpl`, which wraps a `std::vector` |
| `rosidl-buffer-backend`, `rosidl-buffer-backend-registry` | The backend interface, and backends found through pluginlib |
| `cuda-buffer`, `cuda-buffer-backend`, `cuda-buffer-backend-msgs` | CUDA storage, CUDA IPC between processes on one host, with a CPU fallback otherwise. Depends on `nvidia-cuda-toolkit` and `libnvidia-compute-595` |

**Finding: the message types already use it.** In Lyrical, `sensor_msgs/PointCloud2::data`,
`Image::data` and `CompressedImage::data` are `rosidl::Buffer<uint8_t>`, not `std::vector`. So
the ROS bridge's `/points` already goes through `rosidl::Buffer` with the CPU backend. The code
compiled unchanged because the CPU `Buffer` has the vector operations it uses (`assign`,
`data()`, `size()`).

## Copy count today (one 3D scan on `/points`)

| Step | Copies | Where |
|---|---|---|
| Ranges from the bus to points | 1 write; no intermediate buffer | `Bridge.cpp`: x, y, z, intensity and ring are written straight into `cloud.data` (after a zero fill) |
| Into rclcpp | 0 | `publish(std::move(cloud))` |
| Intra-process subscriber | 0 when intra-process communication is on | rclcpp |
| Inter-process: serialisation | 1 | rmw_fastrtps CDR serialisation |
| Inter-process: transport | unverified (TODO(verify)) | Fast DDS shared-memory transport on one host, UDP otherwise |
| Subscriber | 1 | deserialisation into its own `Buffer` |

The sample AMR's top lidar is 16 rings × 900 columns (`amr_diffdrive.urdf`), so 14 400 points ×
20 bytes (18 bytes of fields, padded) = 288 kB per scan, 2.9 MB/s at 10 Hz. The two copies on
the inter-process path are well within a CPU's memory bandwidth. The cost is latency and cache pressure, not throughput.

## Constraints

- **CPU backend:** works today, and needs nothing from us beyond what the bridge does. Building
  the point data in a `std::vector` and moving it in (`Buffer(std::vector&&)`) is also zero-copy.
- **CUDA backend:** needs an NVIDIA GPU, driver 595 and the CUDA toolkit. It is a Tier 2 path
  only. CUDA IPC needs both endpoints on one host (the backend discovers locality) and falls
  back to CPU otherwise.
- **Our GPU lidar is Vulkan.** Its ranges live in a Vulkan buffer. Handing them to a CUDA
  `Buffer` without a copy needs Vulkan–CUDA external-memory interop in `gpu/hal/`
  (`VK_KHR_external_memory_fd` with `cudaImportExternalMemory`). That is risk R11 in
  `docs/design/domains/sensors.md` §6. Until then, a GPU cloud is read back to the CPU (the
  current Tier 1 path) and published through the CPU backend.

## Plan for v0.6 (cars, where camera and lidar bandwidth matter)

1. `gpu/hal/`: export a Vulkan buffer as a file descriptor, and import it into CUDA when CUDA
   is present (Tier 2). Fall back to the readback.
2. Publish lidar clouds and camera images as `rosidl::Buffer` with a `cuda_buffer` backend
   implementation when `bridges.ros2.gpu_buffers` is on and the subscriber is on the same host.
   Keep the CPU backend otherwise.
3. Measure on the self-hosted NVIDIA runner: the copy count end to end (Vulkan → CUDA →
   subscriber), and latency against the CPU path. That is the acceptance this desk study
   could not provide.
4. Now (v0.2): nothing to change. Note in the bridge that `PointCloud2::data` is a
   `rosidl::Buffer`, so the path is ready for a backend swap.
