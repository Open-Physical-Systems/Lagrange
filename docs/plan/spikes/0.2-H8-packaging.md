# Spike 0.2-H8: packaging trial

Date: 2026-10-25. Roadmap item 0.2-H8: "`bloom` dry run for packages without vendor
dependencies; Docker image on `ubuntu:resolute`; decision on buildfarm vs own apt repository
(Q18). **AC:** an image runs the Nav2 demo headless."

## 1. bloom dry run

`bloom-generate rosdebian --ros-distro lyrical`, then `fakeroot debian/rules binary`, on
copies of the packages (debhelper 13.31):

| Package | Result | Package file |
|---|---|---|
| `lagrange_cmake` | built | `ros-lyrical-lagrange-cmake_0.1.0-0resolute_amd64.deb`, 6 kB, installs under `/opt/ros/lyrical` |
| `lagrange_core` | built | `ros-lyrical-lagrange-core_0.1.0-0resolute_amd64.deb`, 175 kB: static library, headers (including `lagrange_plugin.h`), CMake config |

Findings:

- **Our own packages need rosdep keys before a release.** `lagrange_core` build-depends on
  `lagrange_cmake`, and bloom resolves every dependency through rosdep. Until the packages are
  in rosdistro, a local rosdep file maps them to their future package names:
  `packaging/rosdep/lagrange-self.yaml`, generated from the `package.xml` files. A dry run can
  use a private rosdep setup (`ROSDEP_SOURCE_PATH`, `ROS_HOME`) without touching
  `/etc/ros/rosdep`.
- **Debian's hardened flags pass.** The package build adds `-flto=auto`,
  `-D_FORTIFY_SOURCE=3`, `-fstack-protector-strong` and `-fcf-protection`; `lagrange_core`
  compiles without a warning.
- **Static libraries have no runtime `Depends`.** `lagrange_core` is a static library, so its
  package depends on nothing at run time. Consumers find `lagrange_cmake` because they declare
  it themselves. That is correct, but a reviewer should know.
- **Build order is the dependency order.** A real release builds and installs each package
  before the next. The dry run stood in for installing by unpacking the `lagrange_cmake`
  package into a staging prefix and pointing `CMAKE_PREFIX_PATH` at it (no `sudo`).

## 2. Container image

`packaging/container/Containerfile` (Podman or Docker): `ros:lyrical-ros-base-resolute`, the
project's `install_deps.sh`, and a build of the simulator and the demo (no viewer). The default
command runs the Nav2 demo headless for one simulated minute.

Results, 2026-10-25 (Podman 5.7, rootless):

- The image builds in about 17 min (OpenUSD 11 min 45 s of it) and is 3.92 GB.
- **The Nav2 demo runs headless in it** (acceptance). With the built-in drive controller: 6/6
  waypoints, no collision, closest approach 0.54 m, in about a minute.
- **Not every run:** of two consecutive runs, one passed. In the other, Nav2's controller server
  never received `/odom` and the patrol ran out of time. That is the same intermittent ROS
  discovery problem as on the host (`progress.md`, known issues), seen here for the first time
  with the built-in controller too. With ros2_control the spawner hit it in both container
  runs, so the image defaults to `CONTROL=builtin`.

Fixed on the way:

- `SHELL` is ignored by Podman's default OCI image format, so the build calls bash explicitly.
- `lagrange_demos` no longer depends on `lagrange_viewer`. The viewer is optional for the demo
  (`viewer:=false`), and a headless build skips it; the nightly Nav2 job, which also skips the
  viewer, would have failed the same way.
- The Containerfile is excluded from the build context, so editing it does not rebuild
  OpenUSD.

Improvements for later:

- Copy only the `package.xml` files before installing dependencies, so a source change keeps
  the dependency layer.
- A multi-stage image without the build tools (3.92 GB now).
- `ros2controlcli` in the image, for debugging ros2_control.

## 3. Q18: the ROS buildfarm or our own apt repository

The open question was whether the buildfarm accepts long vendor builds and CUDA.

Evidence from Lyrical, 2026-10-25:

- The buildfarm builds **vendor packages that fetch sources during the build**:
  `ros-lyrical-mujoco-vendor` (installed here) uses `ament_cmake_vendor_package` with `git`
  as a build tool. Large ones are released too: `aws_sdk_cpp_vendor`, and the `gz_*_vendor`
  family.
- Lyrical's rosdistro has no OpenUSD or Jolt package (checked in `lyrical/distribution.yaml`,
  726 repositories), so `openusd_vendor` and `jolt_vendor` stay ours. It does have
  **`fmilibrary_vendor`**, the FMI library that v0.3's FMU host needs.
- CUDA: the buildfarm's images are plain Ubuntu without NVIDIA's toolkit, and the toolkit's
  licence is not open source. The CUDA packages that are released (`cuda_buffer`) build
  against Ubuntu's `nvidia-cuda-toolkit` package (TODO(verify) how the buildfarm handles that
  dependency).

**Recommendation:**

- Release through the ROS buildfarm for all packages, including `openusd_vendor` and
  `jolt_vendor`: they follow the same pattern as the released vendor packages.
- Keep a project apt repository only for what the buildfarm cannot build: CUDA fast paths
  (v0.6), if `nvidia-cuda-toolkit` turns out not to be usable there.
- Before the first release, run `openusd_vendor` through a local `ros_buildfarm` devel job.
  It is the longest build, about 20 to 25 min here, and the buildfarm's time limit is not
  checked yet (TODO(verify)).
